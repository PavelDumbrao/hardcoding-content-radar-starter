# Правила для ИИ-агента

Этот файл — рабочий контракт для Codex, Claude Code, Cline и любого другого coding agent.
Читай его перед началом работы.

## Главный принцип проекта

**ИИ управляет исследованием. Код считает метрики.**

- Агент (LLM) понимает запрос, расширяет тему, выбирает инструменты, объясняет смысл и предлагает идеи.
- Обычный Python-код делает всё, что можно посчитать: просмотры, скорость роста, outlier,
  свежесть данных, дедупликацию, запись в базу.
- LLM **никогда** не придумывает просмотры, лайки, даты, ссылки и score.
  Любая цифра берётся только из результата инструмента и имеет поле `observed_at`.

Если данных нет — сервис говорит об этом прямо. Это не баг, а требование.

## GitHub — источник правды

1. Перед работой проверь remote и синхронизируйся с `origin/main`.
2. Не меняй `main` напрямую для заметных изменений.
3. Создай отдельную feature-ветку.
4. Изучи `PROJECT.md`, `TASKS.md`, `README.md` и последние изменения.
5. Делай небольшие изменения с понятным результатом.
6. После законченного блока сделай понятный commit на русском языке.
7. Перед push запусти доступные локальные проверки.
8. После push создай Pull Request по шаблону `.github/pull_request_template.md`.
9. Проверь GitHub Actions.
10. Merge в `main` только после успешных проверок.
11. После merge убедись, что `origin/main` содержит итог.
12. Не проси пользователя выполнять Git-команды вручную, если у тебя есть Git и GitHub.
13. Не коммить `.env`, токены, ключи, пароли и другие секреты.
14. Если пользователь открывает новый чат — сначала восстанови контекст из репозитория,
    а не полагайся на память разговора.
15. Не говори «готово» без доказательства: commit, PR, зелёные checks, ответ живого сервиса.

## GitHub CLI (gh)

Если `gh` доступен — используй его как основной интерфейс к GitHub.

1. Проверь наличие `gh`.
2. Если его нет — установи официальный GitHub CLI подходящим для текущей ОС способом.
3. Проверь авторизацию: `gh auth status`.
4. Если авторизации нет — попроси пользователя пройти browser/device login.
   Не проси токен в чате.
5. При необходимости настрой Git: `gh auth setup-git`.
6. Никогда не печатай токены и не используй `gh auth token` без доказанной необходимости.

Через `gh` выполняй сам: создание и просмотр репозиториев, Pull Requests, diff и checks,
ожидание GitHub Actions, merge после зелёных checks, Issues, Releases, workflow runs.

## Карта проекта

```
apps/api/app/
  config.py          настройки из окружения (.env)
  db.py              подключение к базе и создание схемы
  models.py          таблицы: creators, videos, video_snapshots, research_runs, source_events
  schemas.py         контракты данных (NormalizedVideo, evidence, ответы API)
  adapters/          источники данных по единому контракту
    base.py          SocialSourceAdapter — общий интерфейс
    youtube.py       YouTube Data API v3
    vk.py            VK API
    instagram.py     Instagram через Apify
    registry.py      реестр источников и честный статус доступа
  services/
    metrics.py       детерминированные расчёты: velocity, outlier, trend score
    store.py         дедупликация, снапшоты метрик, аудит вызовов
  agent/
    agent.py         сборка агента и системная инструкция
    tools.py         инструменты агента (что он умеет вызывать)
    deps.py          контекст запуска и накопление доказательств
  api/
    routes_chat.py   POST /api/chat
    routes_system.py /healthz и /api/sources
  web/               чат-интерфейс (index.html, app.js)
docs/                архитектура, запуск, деплой, что делать дальше
deploy/              скрипт деплоя и инициализация базы
scripts/             проверка проекта перед PR
```

## Ключевые точки входа

- `POST /api/chat` — основной сценарий: запрос пользователя → агент → инструменты → ответ с источниками.
- `GET /api/sources` — честный статус источников: настроен или нет и какой переменной не хватает.
- `GET /healthz` — живость сервиса и какая модель подключена.

## Как добавить новый источник

1. Создай `apps/api/app/adapters/<platform>.py`.
2. Отнаследуйся от `SocialSourceAdapter` и реализуй методы:
   `search_videos`, `get_video`, `get_comments`, `refresh_metrics`, свойство `configured`.
3. Приводи ответ площадки к `NormalizedVideo` из `schemas.py`. Никаких «своих» форматов.
4. Обязательно заполняй `metrics.observed_at` — время, когда цифра была получена.
5. Зарегистрируй адаптер в `adapters/registry.py` и добавь подсказку,
   какой переменной окружения не хватает для его включения.
6. Добавь источник в `SOURCES` в `apps/api/app/web/app.js`.
7. Опиши в `docs/architecture.md`, если меняется контракт.

Ошибки источника возвращай через `SourceError` с понятным текстом: агент должен
объяснить пользователю причину, а не упасть.

## Как менять расчёты метрик

Всё, что считает цифры, живёт в `apps/api/app/services/metrics.py`.

- Меняешь формулу — оставь комментарий, почему так правильно.
- Не превращай метрику в «магическое число»: у каждого коэффициента должно быть объяснение.
- Если данных недостаточно для честного расчёта (например, у автора меньше трёх видео),
  возвращай `None`, а не выдуманное значение.
